54|
55|```
56|[가입]
57|앱: 번호 입력
58| → POST /auth/phone/send        레이트리밋 검사 → 6자리 생성 → 해시 저장 → SOLAPI 발송

64|                                   └ 2건+: 409 PHONE_AMBIGUOUS
65|앱(신규만): 이름 입력
66| → POST /auth/phone/signup      app_users 생성 → custom_token
67|앱: signInWithCustomToken(custom_token) → 이후 ID 토큰 체계는 기존과 완전히 동일

81|## 3. 마이그레이션 `infra/migrations/00XX_phone_auth.sql`
82|
83|### 3.1 유니크 범위 — 중요
84|
85|전역 유니크가 아니라 **로그인에 번호를 쓰는 역할에만** 건다. 식당 사장이 관리자 계정과 사용자앱 계정을 같은 번호로 갖는 것은 정상 상황이며, 관리자 계정은 이메일로 로그인하므로 번호가 로그인 키가 아니다.
86|
87|```sql
88|begin;
89|
90|-- 저장 시점 정규화
91|update public.app_users
92|   set phone = regexp_replace(phone,'[^0-9]','','g')
93| where phone is not null and phone <> regexp_replace(phone,'[^0-9]','','g');
94|
95|alter table public.app_users
96|  add column if not exists phone_verified_at timestamptz;
97|
98|alter table public.app_users drop constraint if exists app_users_phone_normalized_check;
99|alter table public.app_users add constraint app_users_phone_normalized_check
100|  check (phone is null or phone ~ '^010[0-9]{8}$');
101|
102|-- 로그인 키가 되는 역할에만 유니크.
103|-- company_admin / merchant_admin / platform_admin은 이메일 로그인을 유지하므로 제외한다.
104|create unique index if not exists uq_app_users_phone_login
105|  on public.app_users(phone)
106|  where phone is not null and role in ('customer','employee');
107|
108|-- 인증번호 발송/검증 기록
109|create table if not exists public.phone_verifications (
110|  id           uuid primary key default gen_random_uuid(),
111|  phone        text not null check (phone ~ '^010[0-9]{8}$'),
112|  code_hash    text not null,              -- bcrypt/argon2. 평문 저장 금지
113|  purpose      text not null check (purpose in ('signup_login','change_phone')),
114|  attempts     int  not null default 0,
115|  max_attempts int  not null default 5,
116|  expires_at   timestamptz not null,
117|  verified_at  timestamptz,
118|  consumed_at  timestamptz,
119|  request_ip   inet,
120|  provider_msg_id text,                    -- SOLAPI 메시지 ID
121|  created_at   timestamptz not null default now()
122|);
123|create index if not exists idx_phone_verifications_lookup
124|  on public.phone_verifications(phone, created_at desc);
125|
126|-- 검증 성공 후 가입 완료까지 쓰는 단기 토큰
127|create table if not exists public.phone_verification_tokens (
128|  token       text primary key,            -- 32바이트 랜덤의 해시
129|  phone       text not null,
130|  expires_at  timestamptz not null,
131|  consumed_at timestamptz,
132|  created_at  timestamptz not null default now()
133|);
134|
135|alter table public.phone_verifications       enable row level security;
136|alter table public.phone_verification_tokens enable row level security;
137|revoke all on table public.phone_verifications, public.phone_verification_tokens
138|  from public, anon, authenticated, service_role;
139|grant select, insert, update on table public.phone_verifications       to service_role;
140|grant select, insert, update on table public.phone_verification_tokens to service_role;
141|
142|commit;
143|```
144|
145|- 롤백 스크립트 `00XX_phone_auth_down.sql`도 함께 작성한다
146|- 만료 레코드는 별도 잡 없이 **발송 시점에 7일 지난 행을 같은 트랜잭션에서 삭제**한다
147|
148|### 3.2 역할 변경 시 충돌
149|
150|`customer` → `employee` 승격처럼 역할이 바뀔 때 같은 번호의 다른 로그인 계정이 있으면 UPDATE가 인덱스 위반으로 실패한다. 이는 의도된 동작이다. 관리자웹에서 역할 변경 시 이 에러를 `이미 같은 번호를 사용하는 계정이 있어요`로 변환해 노출한다.

154|## 4. API
155|
156|파일: `services/api/app/routers/phone_auth.py` 신규 + `routers/__init__.py` 등록. 응답 포맷은 기존 라우터와 동일하게 `{"ok","data","error"}`.
157|
158|### 4.1 `POST /auth/phone/send`
159|
160|```json
161|요청 { "phone": "010-1234-5678", "purpose": "signup_login" }
162|응답 { "ok": true, "data": { "expires_in": 180, "resend_after": 60 } }
163|```
164|
165|- 서버에서 정규화(`[^0-9]` 제거) 후 `^010[0-9]{8}$` 검증. 실패 시 `400 INVALID_PHONE`
166|- 6자리는 `secrets.randbelow(900000)+100000`. **`random` 모듈 금지**
167|- 해시로만 저장. 평문·로그 출력 금지 (`logging_filters.py` 마스킹 대상에 번호·코드 추가)
168|- 만료 3분
169|- **가입 여부와 무관하게 동일한 응답**을 준다 (계정 존재 여부 노출 방지)
170|- 레이트리밋 초과 시 `429` + `retry_after`
171|
172|| 기준 | 한도 |
173||---|---|
174|| 같은 번호 재발송 | 60초 쿨다운 |
175|| 같은 번호 | 시간당 5회 / 일 10회 |
176|| 같은 IP | 시간당 20회 |
177|
178|- SOLAPI 실패 시 `502 SMS_SEND_FAILED` + 서버 ERROR 로그. 사용자 문구 `문자를 보내지 못했어요. 잠시 후 다시 시도해 주세요.`
179|
180|### 4.2 `POST /auth/phone/verify`
181|
182|```json
183|요청 { "phone": "01012345678", "code": "123456" }
184|
185|응답(기존) { "ok": true, "data": {
186|  "status": "existing", "custom_token": "...", "display_name": "홍길동" } }
187|
188|응답(신규) { "ok": true, "data": {
189|  "status": "new", "verification_token": "...", "expires_in": 300 } }
190|```
191|
192|- 해당 번호의 **가장 최근 미소진 레코드**만 대상. 만료·소진은 `400 CODE_EXPIRED`
193|- 불일치 시 `attempts + 1`, `max_attempts` 도달 시 즉시 소진 처리 + `429 TOO_MANY_ATTEMPTS`
194|- 성공 시 `verified_at`, `consumed_at` 기록 (재사용 차단)
195|- **기존 계정 조회 조건**
196|  ```
197|  app_users.phone = 정규화값  AND  role in ('customer','employee')
198|  ```
199|  관리자·식당 계정을 조회 대상에 넣으면 같은 번호를 쓰는 사장님 계정 때문에 `PHONE_AMBIGUOUS`가 발생한다
200|- 1건이고 `status`가 `left`/`rejected`면 `403 ACCOUNT_UNAVAILABLE`
201|- 2건 이상이면 `409 PHONE_AMBIGUOUS` — 자동 선택·자동 병합 금지
202|- 커스텀 토큰:
203|  ```python
204|  auth.create_custom_token(f"phone_{phone}",
205|      {"greeneatgo_internal_id": str(existing_id)})
206|  ```
207|- `phone_verified_at = now()` 갱신
208|
209|### 4.3 `POST /auth/phone/signup`
210|
211|```json
212|요청 { "verification_token": "...", "display_name": "홍길동" }
213|응답 { "ok": true, "data": { "custom_token": "...", "account_id": "uuid" } }
214|```
215|
216|- 토큰 미소진·미만료 검증 → 소진 처리
217|- `display_name` 공백 제거 후 1~20자, 실패 시 `400 INVALID_NAME`
218|- UID `phone_{번호}` → `uuid5(FIREBASE_UID_NAMESPACE, uid)`로 `app_users.id` 생성
219|- `role='customer'`, `status='active'`, `phone`, `phone_verified_at=now()`
220|- 회사 연결(초대코드)은 **기존 `invites.py` 흐름 그대로**. 여기서 처리하지 않는다
221|- 동시 요청 대비: 유니크 위반 시 기존 계정으로 간주하고 커스텀 토큰 발급 (멱등)
222|
223|### 4.4 `POST /auth/phone/change` (로그인 상태)
224|
225|`send(purpose='change_phone')` → `change`에 `verification_token` 전달 → `phone`, `phone_verified_at` 갱신. **Firebase UID는 바꾸지 않는다**(내부 ID가 클레임으로 유지되므로 무해). 다음 재로그인부터 새 번호로 조회된다.

342|## 10. 완료 조건
343|
344|1. 신규 사용자가 번호+인증번호만으로 가입되고, 앱 재실행 시 로그인 상태가 유지된다
345|2. **`04a8c9fd-11f1-5dee-b4e8-92e73571745c` 계정이 `01092341313`으로 OTP 로그인했을 때 기존 주문 45건이 그대로 보인다** (스테이징 또는 배포 직후 실계정 검증)
346|3. 같은 번호로 60초 내 재발송을 요청하면 429와 남은 초를 받는다
347|4. 인증번호를 5회 틀리면 그 코드가 무효화되고 재발송 없이는 진행할 수 없다
348|5. 만료·기사용 인증번호로는 로그인되지 않는다
349|6. `verification_token`을 두 번 쓰면 두 번째는 거부된다
350|7. 로컬에서 같은 번호의 `customer` 계정을 2건 만들면 유니크 위반으로 실패한다 (검증 후 테스트 행 제거)
351|8. **`merchant_admin` 계정과 `customer` 계정이 같은 번호를 가져도 저장되며, 그 번호로 OTP 로그인하면 `customer` 계정으로만 로그인된다**
352|9. 관리자가 `010-1234-5678`, `01012345678` 어느 형식으로 검색해도 같은 고객이 나온다
353|10. 서버 로그 어디에도 인증번호 평문이 남지 않는다
354|11. `ENV=production`이고 `SMS_DRY_RUN=true`면 서버가 부팅에 실패한다
355|12. SOLAPI 발송 실패가 500이 아니라 502 + 사용자 친화 문구로 반환된다
356|13. 관리자웹·식당·업체 관리자 로그인에 diff가 없다
